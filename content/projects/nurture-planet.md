## 问题

民办幼儿园需要把老师端的日常园务、家长端的通知与成长记录、管理后台的园所管理连成一套系统。市面上通用产品往往假设园所流程一致，但实际每家庭园在分班、接送、通知、权限上的规则都不一样。

这套 SaaS 的目标不是做一个「功能很多」的产品，而是把园所最常用的流程收敛成可配置的模块，让老师和家长都能在微信里完成日常操作。

## 约束

- 一个人完成产品方案、后端、两个小程序和管理后台；
- 周期约 2.5 个月；
- 多租户：所有业务数据必须按园所隔离，儿童照片只对授权家长可见；
- 客户环境与儿童数据不能进入公开仓库，对外内容需要脱敏。

## 我做了什么

- 后端使用 Go + Gin + GORM + MySQL + Redis，权限用 Casbin，依赖注入用 Wire；约 300 个接口、70 张表，约 7 万行（含约 2.2 万行测试）。
- 老师端与家长端使用 uni-app + Vue 3，管理后台使用 Nuxt 3 + Element Plus + Pinia + ECharts；三端合计约 130 个 Vue 组件。
- 多租户采用共享表 + 租户列，repository 层强制注入租户条件，测试覆盖跨园所读取。
- 人脸识别抽象为 Provider 接口，接入腾讯云 IAI 做 1:N 检索；供应商方案变化时只替换实现层。
- 用一条自建的多 agent 流水线组织切片、契约、评审与证据留存；代码由 agent 生成，人工评审和测试兜底。

## 架构与关键取舍

**共享表 + 租户列**，而不是每个租户一个 schema。前者实现简单，但要求每一层都记得带租户条件；我把「忘记租户条件」当成最高级别缺陷，用 repository 强制注入、code review 和跨租户测试三道防线兜住。

**契约优先**。`backend/api/` 是接口形状的唯一真相源，改接口先改契约，三端照着契约写；契约不一致时测试先失败。

**可替换边界**。人脸识别、对象存储、短信等外部依赖都收敛到接口后面。对一人项目来说，这比「选对某个供应商」更重要，因为变化总会发生，而你没有团队去追每一个变化。

## 结果

约 2.5 个月交付约 14 万行代码，三端可用，核心园务流程上线。代码行数只说明生成速度，不说明可维护性；真正重要的是返工率、评审通过率和线上故障率，这些在我的复盘文章里有更详细的记录。

## 复盘

如果重来一次，我会把切片再切小一点、真机验证再早一点、契约测试再多一点。多 agent 流水线不是「让 AI 自动写完」，而是把一个人的判断力放到切片、契约和评审这三个位置上。
